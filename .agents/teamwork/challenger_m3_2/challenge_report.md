## Challenges

### [Low] Challenge 1: Array-Type Payloads in `importJSON`

- **Assumption challenged**: The storage manager's `importJSON` method assumes that valid imported backup payloads are JSON objects representing `AppStorageData`.
- **Attack scenario**: An external user or automated script uploads a JSON array string (e.g. `"[]"` or `"[1, 2, 3]"`). In JavaScript, `typeof [] === 'object'` evaluates to `true`, and `![]` evaluates to `false`. Consequently, the check `if (!parsed || typeof parsed !== 'object')` allows arrays to pass into `sanitize()`.
- **Blast radius**: The `sanitize` method treats the array as an object without known keys, resulting in all fields falling back to `DEFAULT_STORAGE_DATA`. This effectively resets the user's active session and logs to default values rather than rejecting the file with an import error.
- **Mitigation**: Add an explicit array guard in `importJSON` and `sanitize`: `if (!parsed || typeof parsed !== 'object' || Array.isArray(parsed))`.
- **Current status**: Minor edge case. Ordinary JSON exports generated by `storageManager.exportJSON()` are strictly objects (`{ ... }`) and always import with 100% fidelity.

### [Low] Challenge 2: Non-Finite Number Filtering in Mobility Input

- **Assumption challenged**: Runtime mobility measurements entered programmatically must strictly be finite floating-point numbers.
- **Attack scenario**: Direct API invocation with `Infinity` or `-Infinity`.
- **Blast radius**: Handled defensively in `validateMobilityEntry` via `Number.isFinite(entry.value)` validation, which returns `"Value must be a valid finite number"`. In the UI layer, `<input type="number">` prevents users from typing non-numeric characters.
- **Mitigation**: Ensure `Number.isFinite()` remains active on all numeric validation paths.
- **Current status**: Resolved and verified.
